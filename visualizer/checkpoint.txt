Estructura propuesta

Siguiendo el mismo patrón que  BaseModel / BaseDataset  +  registry.py , convertiría  semantic_search.py  (archivo único) en un paquete  visualizer/backend/semantic_search/  con una clase base que solo expone los dos puntos que cambian según la fuente de datos:

visualizer/backend/semantic_search/
    __init__.py
    engine.py          # lógica genérica actual (SearchJob, SearchResult, heap top-k, hilo en background)
    cache.py           # el actual search_cache.py, sin cambios de fondo
    basesource.py       # NUEVO: BaseSemanticSearchSource (ABC)
    sources/
        default.py     # DefaultImageSource: comportamiento actual (carpeta de imágenes normales)
        <tuyo>.py       # futuro: TiledImageSource específico de tu caso de uso

 BaseSemanticSearchSource  (ABC)

Solo dos métodos abstractos, análogos a lo que ya hicisteis en  basemodel.py / basedataset.py :

@dataclass
class ScanUnit:
    id: str                       # clave única para la caché (p.ej. "img.tif::tile_3_7")
    group_key: str                 # clave de deduplicado "un resultado por X" (p.ej. la imagen origen)
    inference_input: str | Path | np.ndarray   # lo que se pasa a model.get_batch_embeddings

class BaseSemanticSearchSource(ABC):
    @abstractmethod
    def iter_scan_units(self, folder: Path) -> Iterator[ScanUnit]:
        """Enumera las unidades de trabajo a inferir (imagen completa, tile, etc.)."""

    @abstractmethod
    def render_result_preview(self, result: SearchResult) -> tuple[bytes, str]:
        """Devuelve (bytes, media_type) de una previsualización recortada/reescalada,
        generada en memoria, sin tocar disco. El frontend la recibe como file/bytes."""

•  DefaultImageSource  (comportamiento actual):  iter_scan_units  = una unidad por imagen del folder ( group_key == id == path );  render_result_preview  = lee el fichero de disco y devuelve sus bytes tal cual (reemplaza el  FileResponse(image_path)  actual).
• Tu fuente específica (tiles):  iter_scan_units  abre cada imagen enorme con lectura por ventanas (sin cargarla entera) y genera un  ScanUnit  por tile con  inference_input  como array de numpy (o ruta a un tile materializado si el modelo solo acepta paths — habría que decidirlo);  render_result_preview  reabre la imagen origen, recorta la región alrededor del bbox detectado con algo de margen, la reescala a un tamaño que WebView pueda manejar, la codifica a JPEG/PNG en memoria y devuelve los bytes — nunca escribe nada a disco.

Cambios en piezas existentes

•  registry.py : añadir  register_semantic_search_source  /  SEMANTIC_SEARCH_SOURCE_REGISTRY , igual que  MODEL_REGISTRY / DATASET_REGISTRY .
•  engine.py  (el actual  run_semantic_search ): en vez de  iter_images_recursive  + asumir "un resultado por imagen", itera  source.iter_scan_units(folder) , agrupa/dedupe por  unit.group_key  en lugar de por  image_path , y la caché ( cache.py ) se indexa por  unit.id  genérico en vez de por ruta de imagen (el esquema SQL no cambia, solo el significado del string).
•  app.py :  SemanticSearchRequest  gana un campo  source_type: str  (elegido del registro, igual que  model_type ); el endpoint  get_semantic_search_result_image  deja de hacer  FileResponse(image_path)  y en su lugar llama a  source.render_result_preview(result)  devolviendo  Response(content=bytes, media_type=media_type)  — así nunca se sirve/guarda la imagen gigante entera, solo el recorte final.
•  basemodel.py : posiblemente ampliar  get_batch_embeddings  para aceptar también  np.ndarray  además de  str | Path  (si los tiles se generan en memoria en vez de materializarse a fichero temporal) — a decidir cuando implementemos tu fuente concreta.

Con esto, para soportar un nuevo tipo de dataset/fuente solo tendrías que crear un fichero en  sources/  implementando esas dos funciones y registrarlo con un nombre, sin tocar  engine.py ,  cache.py  ni  app.py .
